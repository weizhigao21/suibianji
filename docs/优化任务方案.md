# 随便记 · 优化任务方案

> 版本 v1（2026-11-23）· 适用代码状态：main 分支 0 提交、src 约 2.8k 行、单文件 exe 38.7MB

## 一、方案概要

三条主线，按危害排序，不混在一起做：

| 主线 | 要解决的问题 | 对应阶段 |
| --- | --- | --- |
| 不丢数据 | 目录漂移、双进程覆盖、备份单点、改不了主密码 | P0 |
| 能持续维护 | 2275 行单文件、无锁依赖、无 CI、零提交 | P1 |
| 真的好用 | 剪贴板、快捷键、详情面板、全局搜索、快速记录 | P2 |

**明确不做（本期）**

- 不用 Rust / C# / Tauri 重写。当前痛点不来自语言，重写约 2～4 周，收益主要是包体和启动时间，用「改 onedir 打包 + Nuitka」一天就能拿到大半。
- 暂不换 SQLite。记录量 <1 万条时，加密 JSON 全量写不是瓶颈，先补版本化 header 和滚动备份。
- 不做云同步。数据模型先留出「多库 + 导出」接口，等真有需求再设计。

**总工作量估算**：约 19 人天，分 4 个里程碑。P0 约 4 天，可以先独立发一版。

## 二、仓库命名

推荐仓库名：**`suibianji`**（GitHub 仓库全名 `suibianji`，本地目录可继续叫 `随便记`）。

理由：这个名字已经在代码里落地了——`KEYRING_SERVICE = "suibianji"`、`suibianji.spec`、打包产物 `suibianji-1.0.0-win64.zip`。仓库名跟着它走，Keyring 条目、spec 文件、发布包、仓库地址四处一致，不用改任何常量，也不会让老用户升级时找不到自己的数据。

备选方案对比：

| 名称 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| `suibianji` | 与代码/产物一致，零迁移成本 | 对英文用户不可读 | **采用** |
| `suibianji-vault` | 名字自带品类，搜索友好 | 与 keyring service、zip 名不一致，需同步改 | 备选 |
| `paperlight` | 呼应「纸间 · Paperlight」主题 | 丢掉了产品本名，老用户认不出 | 不建议 |
| `local-vault` / `notes-vault` | 通用易记 | 与已有标识完全脱节，重名概率高 | 不建议 |

配套统一（一次性做完，0.5 人天）：

- 包名 `src/suibianji/`，`python -m suibianji` 作为唯一入口，`main_qt6_redesigned.py` 保留为兼容 shim（`from suibianji.__main__ import main`）。
- exe / 安装包 / zip 统一 `suibianji-<version>-win64`，版本号收敛到 `suibianji/__init__.py` 的 `__version__`。
- README 标题改为「随便记 · Suibianji」，GitHub About 写一句：`本地加密的个人记录管理器 · AES-256 + PBKDF2 · Windows`。
- 仓库描述里注明 MIT，tag 规则 `v1.0.0`，release 资产挂 zip + sha256。

## 五、风险与回滚

- **改主密码（T05）与格式升级（T21）都会重写加密数据**：改动前强制生成一份完整备份；写入后用新密钥回读校验，校验失败自动还原；提供 `tools/verify_vault.py` 供用户自检。
- **拆包（T08）可能打断打包链路**：保留 `src/main_qt6_redesigned.py` shim，spec 与 bat 双入口并存一个版本周期。
- **打包改 onedir（T25）**：新旧产物并存发布，确认启动时间与体积收益后再下架 onefile。
- **自动锁定（T07）误锁**：锁定时先落盘未保存内容，避免打断正在编辑的对话框。

## 六、通用验收规则

1. 任何触及加密或存储的改动，必须补一条「旧库仍可打开」的回归测试。
2. 每个任务完成时附一段手测清单（3～5 步），写进 PR 描述。
3. 发版前跑 `pytest` + `ruff check` + 打包一条快速验证脚本（`scripts/release_check.ps1`，随 T09 一起建）。
4. 功能改动一律走分支 + PR，不再直接改主干。
